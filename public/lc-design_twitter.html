Every approach, with the expensive line circled — and carried forward so you can see what got fixed and what's still on the hook.

choice 1 — storing tweets

A dict of lists

choice

tweetMap[userId] → list of [timestamp, tweetId]

why

A dict gives instant lookup of "this user's tweets" by id — no scanning. A list works because tweets always get appended in the order they're posted, so the list is already sorted by time for free. No extra sort needed just to store a new tweet.

choice 2 — storing who follows whom

A dict of sets

choice

followMap[userId] → set of followeeIds

why

Same instant lookup by id. A set, not a list, because following someone twice should do nothing, and the order of followees never matters. A set gives O(1) add / remove / check and refuses duplicates on its own.

choice 3 — posting a tweet

Append it, then tick the counter

what happens

Add the tweet to that user's list, then move the shared counter forward by one.

why

Appending keeps every user's tweets in the order they were posted, automatically — no sorting needed just to store one. The counter ticks up by one no matter who's posting, so two tweets can never tie, and a bigger number always means "happened later."

    self.tweetMap[userId].append([self.timestamp, tweetId])
    self.timestamp += 1
approach 1

Collect everything, sort, slice

Grab every tweet from the user and everyone they follow. Sort the combined list by time. Take the top 10.

example
# user 1 follows user 2 and user 3
tweetMap = {
    2: [[0, 'a'], [2, 'b'], [4, 'c']],   # user 2 has posted 3 tweets
    3: [[1, 'x'], [3, 'y']]              # user 3 has posted 2 tweets
}

feed = tweetMap[2] + tweetMap[3]   # 5 tweets combined here, fine at this size
feed.sort(key=lambda t: -t[0])     # sorts all 5 -- but if user 2 had posted
                                    # 4,000 tweets instead of 3, this same line
                                    # sorts all 4,000, every time, to use 10.
the method
def getNewsFeed(self, userId):
    feed = self.tweetMap[userId][:]
    for followeeId in self.followMap[userId]:
        feed.extend(self.tweetMap[followeeId])
    feed.sort(key=lambda x: -x[0])
    return [tweetId for _, tweetId in feed[:10]]

approach 2

Heap merge — stop sorting everything

Only ever look at the newest tweet from each followee. Take whichever is newest overall, then pull that same followee's next tweet into the running. Repeat until you have 10.

Why only the newest tweet from each person? Their tweets are already stored oldest to newest — that's just what happens when you keep appending to a list. So the newest tweet is the only one that could possibly win right now; everything else that person has posted is older, and older can never beat newer. Once we've used a person's newest tweet, then their second-newest becomes worth looking at — never before that.

example — one merge cycle at a time, 2 followees
# user1 follows user2 and user3
# user2's tweets, oldest -> newest: t101 (time 0), t102 (time 2)
# user3's tweets, oldest -> newest: t201 (time 1)

# Step 1: look at ONLY each person's newest tweet
#   user2's newest -> t102 (time 2)
#   user3's newest -> t201 (time 1)

# Step 2: whichever is newest overall wins first
#   t102 (time 2) beats t201 (time 1)  ->  feed = [t102]

# Step 3: user2 just got used up -- do they have another tweet?
#   yes -> t101 (time 0) becomes user2's new candidate

# Step 4: compare again -- t101 (time 0) vs t201 (time 1)
#   t201 wins this round  ->  feed = [t102, t201]

# Step 5: user3 has nothing left. user2 still has t101 -- take it.
#   feed = [t102, t201, t101]

# done -- already newest to oldest, no extra sorting needed
the method
def getNewsFeed(self, userId):
    res, minHeap = [], []
    self.followMap[userId].add(userId)

    for followeeId in self.followMap[userId]:
        if followeeId in self.tweetMap:
            index = len(self.tweetMap[followeeId]) - 1
            ts, tweetId = self.tweetMap[followeeId][index]
            heapq.heappush(minHeap, [-ts, tweetId, followeeId, index - 1])  # flipped: smallest = newest

    while minHeap and len(res) < 10:
        ts, tweetId, followeeId, index = heapq.heappop(minHeap)
        res.append(tweetId)
        if index >= 0:
            ts, tweetId = self.tweetMap[followeeId][index]
            heapq.heappush(minHeap, [-ts, tweetId, followeeId, index - 1])

    return res

approach 3

Optimized heap — remember less, check fewer people first

Two small changes here. First: only remember a user's last 10 tweets — anything older than that was never going to be used anyway. Second: if someone follows 10 or more people, take a quick look at just their newest tweets first, and drop anyone whose newest tweet isn't fresh enough to matter — before doing the real merge.

example — narrowing followees before merging
# 12 followees, only their single newest tweet shown, freshest to stalest:
# N1  N2  N3  N4  N5  N6  N7  N8  N9  N10 | N11  N12
#                                          ^ cut here
#
# N11 and N12 get dropped completely -- even though we never looked at
# any of their OTHER tweets. 10 other people already have something
# newer than N11 or N12's best tweet, so neither could ever win a spot.

postTweet picks up exactly one new line below — the cap. Everything else about it is unchanged from before.

the method
def postTweet(self, userId, tweetId):
    self.tweetMap[userId].append([self.timestamp, tweetId])
    if len(self.tweetMap[userId]) > 10:
        self.tweetMap[userId].pop(0)   # nobody needs more than their last 10 remembered
    self.timestamp += 1

def getNewsFeed(self, userId):
    res, minHeap = [], []
    self.followMap[userId].add(userId)
    followees = self.followMap[userId]

    if len(followees) > 10:
        shortlist = []
        for followeeId in followees:
            if followeeId in self.tweetMap:
                index = len(self.tweetMap[followeeId]) - 1
                ts, tweetId = self.tweetMap[followeeId][index]
                heapq.heappush(shortlist, [ts, tweetId, followeeId, index - 1])
                if len(shortlist) > 10:
                    heapq.heappop(shortlist)   # drops the stalest "newest tweet" -- no flip needed, ts is already raw
        for ts, tweetId, followeeId, index in shortlist:
            heapq.heappush(minHeap, [-ts, tweetId, followeeId, index])
    else:
        for followeeId in followees:
            if followeeId in self.tweetMap:
                index = len(self.tweetMap[followeeId]) - 1
                ts, tweetId = self.tweetMap[followeeId][index]
                heapq.heappush(minHeap, [-ts, tweetId, followeeId, index - 1])

    while minHeap and len(res) < 10:
        ts, tweetId, followeeId, index = heapq.heappop(minHeap)
        res.append(tweetId)
        if index >= 0:
            ts, tweetId = self.tweetMap[followeeId][index]
            heapq.heappush(minHeap, [-ts, tweetId, followeeId, index - 1])

    return res
why the minus sign

Python's heap always hands you the smallest number it's holding. But the timestamp only ever counts up, so the newest tweet always has the biggest number. To make the heap hand us the newest tweet first, we store it negative — the biggest real number becomes the smallest negative one, and the heap gives that to us first, which is exactly the tweet we want.

The shortlist heap doesn't need this trick. Its job is the opposite: throw out the oldest of the bunch whenever it overflows past 10. "Oldest" already means "smallest raw number" — no flip required there.

what got fixed

That's the whole improvement: once the heap is capped at 10, every push and pop does roughly the same small amount of work, no matter how many people you follow. You still do that small bit of work once for each followee, but none of them can ever make a single step slower than any other. And you can't really do better than glancing at each followee at least once — that's the only way to know whether they belong in the top 10.

What we actually did

Tweets live in a dict so you can jump straight to any user's list by id, and a list keeps them in order automatically since new tweets just get appended. Followees live in a set, so following someone twice does nothing and order never matters. Posting a tweet appends it and bumps one shared counter, so nothing ever ties and "bigger number" always means "newer."

The naive feed dumps every followee's tweets into one pile and sorts the whole thing — simple, but it sorts tweets that never had a shot at the top 10. The heap version fixes that by only ever looking at the single newest tweet from each followee: take whichever is newest, then check that same person's next tweet, and repeat until the feed has 10. The final version trims it further — nobody's tweets beyond their last 10 are kept, and if someone follows a lot of people, only the 10 with the freshest tweets are even allowed into the real merge.
