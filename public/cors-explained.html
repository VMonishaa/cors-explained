01 — the origin story

Why does CORS exist at all?

To understand CORS, you have to first understand the attack it's defending against. Imagine you're logged into your bank. Your browser has quietly saved a session cookie — a small proof that says "this person is authenticated." You can't see it. It just sits there.

Now you open a sketchy website in another tab. Without any protection, that website's JavaScript could silently run this:

evil.com running in your browser
fetch('https://mybank.com/api/transfer', {
  method: 'POST',
  credentials: 'include',  // attaches your bank cookie automatically
  body: JSON.stringify({
    to: 'attacker-account',
    amount: 50000
  })
})

Your browser would attach your bank's session cookie automatically — because that's how cookies work. The bank would see a valid session. It would think it was you. The transfer would happen. You'd never know.

This is called Cross-Site Request Forgery (CSRF). It's not hypothetical. It's the reason the browser needed a hard rule.

The uncomfortable truth: The browser is the last line of defense between a malicious website and your users' data on other sites. If the browser doesn't stop it, nothing will — because the server sees a valid cookie and has no way to tell the request came from somewhere unauthorized.
02 — the rule

The Same-Origin Policy

Browsers responded with the Same-Origin Policy (SOP): JavaScript from one origin cannot read data from a different origin. Full stop.

An origin is the combination of three things:

Protocol
https:// + Domain
app.example.com + Port
:443 = Origin

Change any one of these and you have a different origin. These are all different from each other:

https://app.example.com        ← base
https://api.example.com        ← ✗ different subdomain
http://app.example.com         ← ✗ different protocol
https://app.example.com:8080   ← ✗ different port

SOP solved the CSRF problem — but it created a new one. The modern web is built on APIs. Your frontend at app.example.com absolutely needs to call your API at api.example.com. With SOP alone, that's completely blocked.

SOP was too strict. It stopped the attacks. But it also stopped legitimate cross-domain communication entirely. The web needed a controlled, opt-in way for servers to say: "I trust that other domain. Let it through." That's CORS.
03 — the mechanism

How CORS actually works

CORS is not a security feature on the server. It is a browser contract. This is the single most important thing to understand about it, and the thing most developers don't fully internalize.

CORS is enforced by the browser, not the server. The server always receives the request. The server always processes it. The browser reads the response headers and decides whether to let your JavaScript see the response — or block it.

When your browser makes a cross-origin request, the server needs to explicitly respond with a header that says which origins are allowed:

Access-Control-Allow-Origin: https://app.example.com

The browser reads that. If the requesting origin matches, it allows the JavaScript to read the response. If the header is missing or doesn't match, the browser blocks the response — even though the request already completed on the server.

The server is hit regardless. The browser decides if JS can read the response.

This is why a CORS error does not mean the server rejected your request. It means the browser rejected the response.

04 — the permission check

What is a preflight request?

For potentially dangerous cross-origin requests — anything beyond a simple GET or POST — the browser does something extra before sending your actual request. It asks for permission first. This is the preflight.

Think of it as the browser saying: "I'm about to send a DELETE request with an Authorization header to a different domain. Before I do that, let me check if the server is actually expecting and allowing this."

What triggers a preflight

The browser will preflight if any one of these is true:

triggers preflight
Method: PUT, DELETE, PATCH
Authorization header
Content-Type: application/json
Any custom header
no preflight needed
Method: GET, POST, HEAD
Basic headers only
Content-Type: text/plain
Content-Type: multipart/form-data

The preflight conversation

When your JavaScript calls fetch('/api/user/1', { method: 'DELETE', headers: { Authorization: 'Bearer token' }}), here is what actually happens — completely invisible to your code:

Step 1 — browser sends OPTIONS (you never write this)
OPTIONS /api/user/1 HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: Authorization
Step 2 — server responds to preflight
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, DELETE, PUT, PATCH
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 3600
Step 3 — browser now sends your actual request
DELETE /api/user/1 HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Authorization: Bearer token

Your JavaScript only sees the final DELETE response. The entire preflight exchange is completely invisible to your code. The browser handles it automatically — you never write a second fetch(), you never see the OPTIONS request, you never know it happened.

How does the server know it's a preflight? Not from OPTIONS alone — that's a normal HTTP method that existed before CORS. The signal is the combination of OPTIONS and the Access-Control-Request-Method header. That header is only ever sent by browsers doing CORS preflight. Libraries like rack-cors and the cors npm package check for exactly this combination.

Preflight caching with Max-Age

Sending an OPTIONS request before every API call adds latency. The Access-Control-Max-Age header tells the browser how long to cache the preflight result in seconds. During that time, the browser skips the preflight and sends the actual request directly.

Access-Control-Max-Age: 3600  // cache for 1 hour

Setting it to 0 (as in the configs we saw) forces a preflight on every request — safer during development where configs change frequently, but slower in production.

05 — the vocabulary

CORS headers explained

Response headers (server → browser)

Header What it does
Access-Control-Allow-Origin Which origin is allowed. Can be a specific origin or * (wildcard)
Access-Control-Allow-Methods Which HTTP methods are permitted in the actual request
Access-Control-Allow-Headers Which request headers are permitted
Access-Control-Allow-Credentials Whether cookies and auth headers can be sent cross-origin
Access-Control-Max-Age How long the browser can cache preflight results (seconds)
Access-Control-Expose-Headers Which response headers JavaScript is allowed to read

Request headers (browser → server, set automatically)

Header What it means
Origin Where the request is coming from — set automatically by the browser
Access-Control-Request-Method What HTTP method the actual request will use (preflight only)
Access-Control-Request-Headers What custom headers the actual request will send (preflight only)

The credentials + wildcard trap

This catches everyone eventually. When your frontend needs to send cookies or an Authorization header cross-origin, both sides must opt in — and the wildcard * is explicitly forbidden:

// ✗ This combination is invalid — browser will refuse it
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true

// ✓ This works — explicit origin required with credentials
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true

The browser also requires the client to opt in:

fetch('https://api.example.com/data', {
  credentials: 'include'  // must explicitly opt in on the JS side too
})
06 — in the real world

How it looks in real code

Rails with rack-cors

Rails.application.config.middleware.insert_before 0, Rack::Cors do
  allow do
    origins do |source, env|
      # source = the Origin header value from the request
      # env = full Rack environment (all request headers etc.)
      allowed_origins.any? { |pattern| pattern.match?(source) }
    end

    resource '/api/v1/*',
             headers: :any,
             methods: %i[get post put patch delete options head],
             max_age: 0,        # no preflight caching
             credentials: true  # allow cookies + auth headers
  end
end

def allowed_origins
  JSON.parse(ENV.fetch('ALLOWED_ORIGINS', '[]')).map do |origin|
    OriginPatternConverter.convert_to_regexp(origin)
  end
end

The origins block receives the incoming Origin header as source. The browser sets this automatically. rack-cors extracts it and passes it into your block. You match it against patterns built from an environment variable — this keeps allowed origins outside of code and configurable per environment.

Node.js / Express with cors package

app.use(
  '/api/v1',
  cors({
    origin: (origin, callback) => {
      // origin is undefined for same-origin requests
      // or non-browser tools like curl, Postman
      if (!origin) {
        return callback(null, false); // skip CORS headers — not needed
      }
      if (isOriginAllowed(origin)) {
        return callback(null, origin); // allow — sets exact origin in header
      }
      return callback(null, false); // deny — no ACAO header → browser blocks
    },
    credentials: true,
    methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE', 'OPTIONS', 'HEAD'],
    maxAge: 0,
  }),
);
Why callback(null, origin) and not callback(null, true)? Because credentials: true requires an explicit origin in the response header, not a wildcard. Passing the actual origin string back makes the cors package write Access-Control-Allow-Origin: https://your-exact-origin.com instead of *.

What happens to requests with no Origin header

When origin is undefined (same-origin browser request, or a tool like curl or Postman), the code calls callback(null, false). This does not block the request. It just skips adding CORS headers to the response — because there's no browser enforcement happening anyway. The request still reaches your controller and responds normally.

07 — the gotchas

Common mistakes and misconceptions

The misconception
The reality
"CORS error means the server rejected my request"
The server responded fine. The browser blocked the response because CORS headers were missing or wrong.
"Use Access-Control-Allow-Origin: *, it always works"
Breaks the moment you need cookies or Authorization headers. Must be an explicit origin when credentials are involved.
"CORS protects my server"
CORS protects your users' browsers from malicious sites. Your server is still hit on every request, CORS or not.
"I need to add CORS headers to my request"
CORS headers belong on the response, set by the server. Browsers set request headers automatically — you can't override Origin.
"curl works but my browser doesn't — it's a browser bug"
CORS is enforced by browsers only. curl has no Same-Origin Policy. Working in curl just means the server responds — it says nothing about your CORS config.
08 — the fix

How to get it right

Never reflect the Origin header blindly

// ✗ The vulnerable pattern — seen in every breach above
const origin = req.headers['origin'];
res.setHeader('Access-Control-Allow-Origin', origin); // anything goes

// ✓ The safe pattern — validate first
const ALLOWED_ORIGINS = [
  'https://app.mycompany.com',
  'https://staging.mycompany.com'
];

const origin = req.headers['origin'];
if (ALLOWED_ORIGINS.includes(origin)) {
  res.setHeader('Access-Control-Allow-Origin', origin);
}

Be careful with regex validation

The dot character in regular expressions matches any character — not just a literal dot. This is how api.example.com becomes exploitable as apiXexample.com:

// ✗ Unescaped dot — matches apiXexample.com, api-example.com
if (/api.example.com/.test(origin)) → allow

// ✓ Escaped dot
if (/api\.example\.com/.test(origin)) → allow

The checklist

Before you deploy any CORS config

  • Validate the Origin header against an explicit allowlist — never reflect it directly
  • Never use credentials: true with wildcard * — they are mutually exclusive
  • Include OPTIONS in your allowed methods — required for preflight to work
  • Escape dots in any regex origin patterns (\. not .)
  • Test with a fake origin: send a request with Origin: https://evil.com and check if it gets reflected back
  • Set max_age to a reasonable value in production (e.g. 86400) to avoid unnecessary preflight on every request
  • Don't allow localhost or null origins in production configs
  • CORS is not your auth layer — you still need JWT, sessions, or API keys
closing thought

One line to remember

"CORS is the browser asking the server: do you trust this website? The server answers via response headers. The browser enforces it."

The browser is doing its job. Always has been. The question is whether your config helps it do that job — or accidentally breaks it by trusting everything.

CORS is the kind of thing that seems simple and isn't. The "easy fix" of reflecting the origin back is always right there, tempting you when something is blocked and you just want it to work. Now you know what's actually at stake when you make that choice.

Now you know what it's actually protecting. Use that.
